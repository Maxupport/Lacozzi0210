# 維運手冊

## 服務依賴

| 服務 | 用途 | 擁有者／管理入口 | 備份或回復狀態 |
| --- | --- | --- | --- |
| GitHub | 程式碼與版本管理 | 待確認 | Git 歷史 |
| Vercel | Next.js 部署 | 待確認 | 上一 Deployment 回復待驗證 |
| PostgreSQL | 主要內容與帳號資料 | 待確認 | 待確認 |
| Supabase Storage | 公開媒體檔案 | 待確認 | 待確認 |
| 報價 webhook | 報價表單處理 | 待確認 | 待確認 |
| Notion | 歷史資料來源 | 待確認 | 是否仍使用待確認 |

## 事故優先順序

1. 保護帳號、個人資料與正式資料。
2. 恢復首頁與報價等核心公開功能。
3. 恢復後台內容管理。
4. 保存錯誤證據與時間線。
5. 系統恢復後再進行原因分析與長期修正。

## 基本處理流程

1. 確認影響範圍與開始時間。
2. 暫停新的正式部署與 migration。
3. 檢查最近一次部署、環境變數與外部服務狀態。
4. 若最近部署與事故高度相關，回復上一個已驗證版本。
5. 執行核心 smoke tests。
6. 記錄原因、影響、處理方式與預防措施。

## 備份要求

- PostgreSQL：確認自動備份頻率、保存期限、還原位置與負責人。
- Supabase Storage：確認媒體檔案是否有版本、備份或可重建來源。
- Vercel：確認可回復的 Deployment 保存範圍。
- GitHub：確認 Repository 管理權不依賴單一帳號。

尚未完成一次實際還原驗證以前，不得將「平台有備份」視為已具備可回復能力。

## 密鑰事件

若密碼、Token、Cookie、資料庫網址或 Service Role Key 疑似外洩：

1. 立即停止使用該密鑰。
2. 在原服務建立新密鑰並更新正式環境。
3. 驗證服務恢復後撤銷舊密鑰。
4. 檢查 Git 歷史、Build log 與存取紀錄。
5. 記錄受影響範圍與後續措施。

只從目前檔案刪除密鑰並不足以處理外洩事件。

# 開發、驗收與發布流程

> 狀態：草案，等待專案負責人確認。

## 角色分工

### 專案負責人

- 決定品牌、內容與功能優先順序。
- 確認明顯的前台行為或視覺變更。
- 核准正式上線時機。
- 在需要時完成 GitHub、Vercel、資料庫或 Supabase 的登入與授權。

### Codex

- 盤點需求與現況。
- 決定最小安全修改範圍。
- 撰寫 AG 執行規格與驗收條件。
- 檢查程式差異、測試結果與 Preview。
- 判斷是否符合正式上線條件。
- 記錄版本、風險與回復方式。

### AG

- 僅依照 Codex 提供的任務規格執行。
- 不自行擴大修改範圍。
- 補齊規格要求的測試與文件。
- 回報修改檔案、測試結果、已知限制與風險。
- 發現規格外問題時先回報，不順便重構。

## 標準流程

1. 專案負責人提出需求或 Codex 從 Roadmap 選取下一項工作。
2. Codex 建立現況證據、風險等級與驗收條件。
3. 建立短期工作分支。
4. Codex 使用 AG 任務範本交付執行規格。
5. AG 完成修改、自我檢查與測試。
6. Codex 檢查完整 diff，不只閱讀摘要。
7. Codex 重跑必要測試並檢查 Vercel Preview。
8. 若有問題，退回 AG 進行小範圍修正。
9. 涉及前台呈現或重要行為時，由專案負責人確認 Preview。
10. 必要檢查通過後合併至 `main`。
11. 驗證正式部署與核心 smoke tests。
12. 更新 CHANGELOG、版本標籤與發布紀錄。

## 分支策略

- `main`：唯一正式發布分支，必須保持可部署。
- `codex/<主題>`：由 Codex 建立與管理的規劃或實作分支。
- 每個分支只處理一個清楚主題。
- 工作完成後透過 Pull Request 合併。
- 不在 `main` 直接開發。
- 不對 `main` force push。
- 不建立長期 `develop` 分支，避免小型團隊承擔額外同步成本。

## Commit 規則

採用 Conventional Commits：

- `feat:` 新功能
- `fix:` 問題修正
- `docs:` 文件
- `refactor:` 不改變功能的整理
- `test:` 測試
- `perf:` 效能改善
- `security:` 安全改善
- `chore:` 工程與維護設定

Commit 應保持單一目的，不混合無關修改。

## 版本規則

穩定化期間採 `0.x.y`：

- PATCH：不改變預期行為的修正，例如 `0.2.0` → `0.2.1`。
- MINOR：加入向下相容功能，例如 `0.2.1` → `0.3.0`。
- MAJOR：完成基礎治理並確認公開契約後，再評估 `1.0.0`。

達到以下條件後才能評估 `v1.0.0`：

- 核心功能有自動化測試。
- CI 與 Preview 發布流程穩定。
- 資料庫 migration 制度完成。
- 備份與回復流程已驗證。
- README 與主要維運文件完成。
- 已處理最高優先級安全風險。

## Pull Request 必要內容

- 目的與背景。
- 修改範圍。
- 明確列出不修改的範圍。
- 測試結果。
- Preview 連結。
- 資料庫或環境變數影響。
- 風險與回復方式。
- 畫面變更前後比較，若適用。

## 必要檢查

- TypeScript 型別檢查。
- ESLint。
- 單元與整合測試。
- Production build。
- 核心 smoke tests。
- Preview 人工驗證。
- Secret 掃描與相依套件風險檢查，導入方式另行評估。

## 上線原則

- 小型、低風險修改可以個別發布。
- 中高風險修改必須安排明確時段並確認回復方式。
- 資料庫與應用程式修改必須保持向下相容。
- 正式站不是測試環境。
- 上線後立即執行 smoke tests。
- 若核心流程異常，優先回復上一正常版本，再進行原因調查。

## 需要帳號或權限時

Codex 必須先說明：

- 需要登入的平台。
- 需要的權限層級。
- 預計修改的設定。
- 是否影響正式站。
- 完成後如何驗證。

專案負責人不需要在對話中提供密碼、Token、OTP 或私密金鑰。

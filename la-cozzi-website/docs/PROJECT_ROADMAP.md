# 專案接管與優化 Roadmap

> 狀態：草案，等待專案負責人確認。  
> 決策原則：穩定性第一，合理運作第二。

## 目標

將目前已可使用的官網整理成可長期維護、可安全更新、可快速回復的正式專案，同時避免不必要的重寫與前台中斷。

## 不在本輪目標內

- 不全面改版。
- 不重寫已穩定運作的前台或後台。
- 不在缺少備份與 Preview 驗證時修改正式資料庫。
- 不為了統一風格而一次搬動大量檔案。
- 不在沒有實際效益時引進複雜平台或大量相依套件。

## 階段 0：確認治理規則

### 目的

在任何功能修改以前，先確認專案如何被管理。

### 工作

- 由專案負責人確認本文件組。
- 確認 Codex、AG 與專案負責人的分工。
- 確認 GitHub、Vercel、資料庫與 Supabase 的管理權歸屬。
- 確認正式上線需要誰核准。

### 完成條件

- 本 Roadmap 經專案負責人確認。
- 未確認事項已有負責人或處理順序。

## 階段 1：建立安全基準

### 目的

確保現有網站可被驗證、備份與回復。

### 工作

- 建立主要頁面與核心流程 smoke test 清單。
- 記錄正式環境服務依賴與資料流。
- 確認 Vercel 回復上一版本的方法。
- 確認 PostgreSQL 與 Supabase 的備份、保存與還原方式。
- 移除 seed 的預設管理員帳密 fallback。
- 視實際使用情況輪替正式管理員密碼。
- 建立環境變數清單與啟動檢查。

### 完成條件

- 可以說明網站故障時如何回復。
- 可以在不讀取密鑰內容的情況下確認必要環境變數是否齊全。
- 正式帳密不再依賴程式碼內建預設值。
- 至少完成一次備份可用性確認。

### 風險等級

低至中。涉及正式帳密或備份設定的步驟，必須由專案負責人參與。

## 階段 2：專案治理與版本管理

### 目的

讓每次修改都有清楚來源、範圍與版本紀錄。

### 工作

- 重寫 README。
- 建立 `.env.example`，只記錄名稱與用途，不放密鑰。
- 建立架構、環境、資料模型、部署與營運文件。
- 建立 Pull Request、Issue 與 AG 任務範本。
- 採用 Conventional Commits。
- `main` 僅保留可部署版本。
- 每項工作使用短期分支與 Pull Request。
- 建立 CHANGELOG 與語意化版本規則。
- 穩定化期間使用 `0.x` 版本，完成基礎治理後再評估 `v1.0.0`。

### 完成條件

- 新接手者能依 README 在本機啟動專案。
- 每項變更都能追蹤需求、修改、驗收與上線版本。
- `main` 不接受未經檢查的直接修改。

### 風險等級

低。主要為文件與 Repository 設定，不改變前台功能。

## 階段 3：品質與發布護欄

### 目的

讓問題在進入正式站以前被發現。

### 工作

- [x] 清除 ESLint 錯誤與警告（0 錯誤、0 警告，AG-001 完成）。
- 解決 workspace root 與 lockfile 警告。
- [x] 讓 production build 可重現（已驗證通過）。
- [x] 建立持續整合檢查：型別、Lint、Build（AG-001）與 Smoke Tests（AG-002）。
- 建立核心單元與整合測試。
- [x] 建立 Playwright 核心唯讀流程 smoke tests（AG-002 完成）。
- [x] 每個 Pull Request 建立 Vercel Preview。
- 設定必要檢查通過後才能合併。

### 優先測試流程

1. 首頁與主要導覽。
2. 報價表單基本驗證與成功／失敗狀態。
3. 管理員登入、登出與鎖定。
4. 文章建立、編輯、發布與下架。
5. 評論送出、審核與顯示。
6. 夥伴資料管理。
7. 圖片上傳。
8. 權限隔離。
9. sitemap、robots 與主要 Metadata。

### 完成條件

- Pull Request 必要檢查全部通過。
- Preview 可由 Codex 與專案負責人驗證。
- 已知核心流程有自動化保護。
- Build 不依賴不穩定的臨時網路狀態。

### 風險等級

低至中。測試與設定可先獨立加入；修正既有問題時必須分批進行。

## 階段 4：穩健整理

### 目的

處理會長期增加故障與維護成本的技術債，但避免大規模改寫。

### 工作

- 建立 Prisma migration 歷史與執行規範。
- 採用向下相容的資料庫變更方式。
- 將敏感資料存取集中於伺服器端資料存取層。
- 統一輸入驗證、錯誤處理與授權檢查。
- 確認 Notion 舊程式的實際依賴；無依賴且已有替代方案後才移除。
- 建立全站錯誤頁面與合理降級行為。
- 加入公開 API rate limit 與垃圾訊息防護。
- 改善上傳檔案驗證與 Storage 權限。
- 評估 Content Security Policy 與其他安全標頭。

### 資料庫規則

- 先新增、後搬遷、最後移除。
- 不在同一次發布中直接刪除仍可能被舊版本使用的欄位。
- migration 在 Preview 或獨立測試資料庫驗證後才能進入正式環境。
- 執行正式 migration 前先確認備份與回復方式。

### 完成條件

- 資料庫 schema 與 migration 歷史一致。
- 舊整合程式是否保留已有明確決策紀錄。
- 公開寫入端點具有基本防濫用能力。
- 錯誤不會直接造成整個網站無法使用。

### 風險等級

中。必須拆成多個小型 Pull Request，不得一次完成全部整理。

## 階段 5：監控、效能與前台優化

### 目的

在穩定基礎完成後，改善可觀測性與使用者體驗。

### 工作

- 建立錯誤監控、服務可用性監測與告警。
- 收集 Core Web Vitals 與實際使用資料。
- 建立報價流程轉換與失敗指標。
- 優化圖片、字型、JavaScript 與主要頁面載入速度。
- 補齊 H1、canonical、Open Graph 圖片與結構化資料。
- 完善影音頁內容。
- 改善手機版導覽、表單與無障礙操作。
- 根據數據安排後續內容或功能優化。

### 完成條件

- 能及時發現正式站錯誤。
- 優化有實際數據或明確使用者需求支持。
- 前台調整不降低既有轉換流程的可用性。

### 風險等級

低至中，依實際改動範圍判定。

## 建議執行批次

| 批次 | 主題 | 是否改變前台 | 是否需要專案負責人參與 |
| --- | --- | --- | --- |
| A | 文件、版本規則、環境清單 | 否 | 確認規則 |
| B | 帳密 fallback、備份與回復 | 原則上否 | 是 |
| C | Lint、Build、CI | 原則上否 | 檢視結果 |
| D | 核心自動化測試 | 否 | 檢視測試範圍 |
| E | Migration 與資料層整理 | 可能 | 是 |
| F | API 與上傳安全 | 可能 | 視行為變更而定 |
| G | 監控、SEO、效能 | 可能 | 確認重要呈現 |
| H | 新功能與前台體驗 | 是 | 是 |

## 暫停條件

遇到下列情況，該批工作必須暫停，不得直接上線：

- 沒有可用的正式資料備份。
- 無法說明回復方式。
- Preview 與正式環境差異不明。
- 核心測試或 Build 未通過。
- 修改範圍超出原任務規格。
- 發現未預期的資料刪除或權限變更。
- 專案負責人尚未確認明顯的前台行為或品牌內容變更。
